| 수정 방식 | 원본에서 직접 패치 (컨테이너 없음) |

## 2. 확정된 구조

### 2.1 폰트 (`$04:8000`–`$05:FFFF`, 파일 `0x20000`–`0x2FFFF`)
- 16×16, SNES 2bpp, 4단계 음영. 글리프 하나는 2×2 타일이고, 16타일 폭 VRAM형 배치(한 행에 8글리프, 행 간격 `0x200`)를 쓴다.
- 글리프 n → 파일 오프셋 `0x20000 + (n//8)*0x200 + (n%8)*0x20` (하단 타일은 `+0x100`).
- 원문은 글리프 0–668을 쓴다(가나/숫자/기호 0–181, 한자 192–668). 글리프 669–1023은 비어 있다(`0x2A7xx`–`0x2FFFF`: 0 또는 `FF` 채움).
- 판독한 원문 문자표: `data/charmap_jp.tsv` (불확실한 글자는 `uncertain`으로 표시).

### 2.2 텍스트 인코딩
- FFFF로 끝나는 16비트 LE 워드 문자열.
- 워드 `0x0000`–`0x0FFF`: 비트 0–10은 뱅크 내 타일 번호(`(n%512//8)*32 + (n%8)*2`), 비트 11은 폰트 뱅크(`$04`/`$05`)를 고른다.
- 제어 코드: `FFFE` = 줄바꿈(타일맵 1행 = 8px, 16px 텍스트 한 줄은 `FFFE FFFE`), `FFFC`/`FFFD` = 속성 `$4E28`을 ±`$0400`(팔레트 전환), `FFFF` = 끝.
- 공백은 글리프 0.

### 2.3 출력 경로 (소비자)
- `JSL $00:9BE8` PrintString: 입력은 `[$23]` 문자열 포인터, `$20` 타일맵 오프셋. 코드 `$00:9C47`–`9C8B`. 16비트 모드(m0 x0).
  - 문자마다 글리프를 `$7E:4C20`에 복사(`9D3F`)하고, 타일맵 버퍼 `$7E:3800`에 `$4E20+$4E28`부터 연속 4타일을 기록한다.
  - `$4E20`은 동적 VRAM 슬롯 카운터로, 공백을 포함해 문자마다 +4 증가한다. `JSL $00:9B4F`가 64B씩 VRAM으로 DMA한다(ch3, `$2116 = $0204 + slot*8`).
  - 따라서 글리프 수는 VRAM 고정 슬롯이 아니라 **폰트 ROM 용량**(최대 1024)으로 제한된다.
- 호출 지점: `JSL $9BE8` 40곳, `JSL $9B96`(초기화) 38곳. 목록은 §5의 도구로 재생성할 수 있다.
- `$00:9D01`: 타일맵 없이 글리프 목록만 적재하는 변형 경로(호출자 미확인).

### 2.4 확인된 증거
- 글리프 200–202를 한글 "미등록"으로 교체하자 슬롯 화면에 예측대로 표시됐다(선택/비선택 팔레트 유지). 동일 소비자 재사용 PoC 통과.

## 4. 진행/위험 표

| 조건 | 현재 상태 | 다음 증거·대응 |
|---|---|---|
| 한글 글리프 수요 ≤ 1024 | 번역 전이라 미측정. 원문 규모로 보아 800–1100 음절 예상 | 번역 확정 후 음절 집계. 초과하면 비트 12를 뱅크 확장에 쓰도록 `9C47–9C62` 훅(빈 ROM `0xCE000–0xE7FFF` 약 104KB) |
| 한 줄 15자, 조언 창 2줄 | 원문 사용량 관측값. 창 용량은 미확인 | 조언 창 소비자에서 3번째 줄/16번째 칸 허용 여부 측정 |
| 문자마다 VRAM 4타일 소모 | 화면당 한도 미측정 | `$4E20` 상한과 VRAM 배치 확인. 한국어가 원문보다 길 때만 문제 |
| 문자열 모집단 | 휴리스틱 하한 | 호출부 40곳의 포인터 설정과 테이블(`$03:9702`, `$03:FEC2`, `$01:B980` 등)을 역추적해 분모 확정 |
| 메뉴 텍스트 저장 위치(T-UNK) | 미해결 | 메인 메뉴 표시 시 `[$23]` 추적 |
| 이름 입력 | 가나 16×6 격자, R로 탭 전환, B로 삭제 | 한글 입력 방식은 사람이 결정 (D-002) |
| 그래픽 텍스트 | 목록 미작성 | VRAM 캡처로 카탈로그 작성 |
| 체크섬 | 헤더 체크섬 정상 | 제품 빌드에서 재계산 |
